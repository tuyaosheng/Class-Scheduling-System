# 课程配置扩展与跨年级教师防冲突 — 设计文档

日期：2026-08-23
状态：设计已确认，待编写实施计划
关联文档：`docs/superpowers/specs/2026-08-21-中小学排课系统-design.md`（总体设计）、`CLAUDE.md`「六条容易踩的坑」「M7 前置重构」

---

## 1. 背景

课程设置（课程目录增删改查：课程名/学科系/场地/单双周/占位符）已实现并测试通过。用户在此基础上提出三件事，讨论后发现它们互相牵连，必须一起设计：

1. 课程系（family）也要能增删改查，不只是课程。
2. 不同年级开设的课程可能不同，同一课程在不同年级的周课时数也可能不同。
3. 将来要考虑教师跨年级、跨学科任课时的时间冲突检测。
4. 梳理课程设置时发现，现有单双周（心美）机制的配对关系和方向是写死的，教师负荷均衡也只是启发式、不是保证，借这次一并修订（见 3.7 节）。

讨论中进一步明确了两个关键点，直接决定了本文档的设计方向：

- **跨年级防冲突不是"等三年级合并成一个求解模型才做"的事**，而是哪怕一次只排一个年级，只要这个年级里有老师同时在别的年级任课，就必须知道那位老师在别的年级已经占用的真实时间。求解顺序因此变得有意义：先排定的年级会约束后排的年级。
- **格子编号（第几节）不能跨年级直接比较。** 初一、初二、初三很可能每天节数不同、上下课时间也不同（教务后续会提供真实的作息时间表）。跨年级判断"是不是同一个时间"必须锚定在真实时钟时间上，不能假设"第 3 节"在各年级是同一件事。

**明确不做（本文档范围外）：**

- 不做"三个年级揉进同一个 CP-SAT 模型同时求解"（`CLAUDE.md`「M7 前置重构」里 `class_id`/task id 那两处改造）。本设计选的是更轻量的路径——见第 5 节——如果将来真的需要三年级联合优化（而不只是防冲突），那是另一件事，到时候单独设计。
- 不做教师作为独立管理实体的 CRUD。教师身份继续是任课表 Excel 导入产生的姓名字符串，与现状一致，不升级成可在系统里增删的实体。
- 不做作息时间表的解析细节——格式未知，教务确认后再补（见第 7 节）。这次先把"年级日历必须带真实时钟时间"这个约束定下来。

## 3. 数据模型

### 3.1 课程与学科系（回顾，已实现）

`courses.yaml`：`{name, family, venue?, alternate?, external}`，`GET/PUT /api/config/courses` 已支持整份读写、重名校验、悬空引用校验（删除课程时若还被 `plans.yaml` 引用会拦下）、场地新名字自动追加进 `venues.yaml`。

学科系不建独立实体：现在 `family` 除了名字没有任何自己的属性，单独建一张表是过度设计。学科系列表从课程目录里已出现的 `family` 值去重派生。

### 3.2 课程系管理（待实现）

- `CourseSettings.vue` 的"学科系"列从纯文本框换成"下拉选已有 + 可输入新建"（datalist 或自定义组合框）。
- "重命名学科系"不需要专门的后端接口。本质是把所有该 family 的课程一起改字符串，前端批量改完整批走现有 `PUT /api/config/courses` 即可。

### 3.3 课程计划增删（待实现）

`plans.yaml` 的结构（按年级分 dict）已经支持"不同年级开设的课程不同、课时数不同"——`初一`/`初二` 现在就是空字典 `{}`。缺口在 `SettingsPanel.vue`：现在只能编辑**已有条目**的课时数，不能增删条目，所以初一/初二实际上没法通过 UI 配置。

要补的：

- course picker（下拉）：列出课程目录里**非占位符**（`external: false`）的课程，排除这个年级 plan 里已经有的
- "添加"按钮把选中课程加入表格，默认课时 0，教务再填具体数字
- 每行加"删除"按钮

后端 `/api/config/plan` 已经接受任意 dict 提交、`validate_plan`/`resolve_plan_key` 已经校验课程/学科系是否存在，这部分不用改。

### 3.4 年级日历（新增 `calendars.yaml`）

```yaml
grade_calendars:
  初三:
    days: [周一, 周二, 周三, 周四, 周五]
    periods:
      - {index: 1, clock_start: "08:00", clock_end: "08:45"}
      - {index: 2, clock_start: "08:55", clock_end: "09:40"}
      # ……
    reserved_slots:
      - {day: 0, period: 9, label: 班会}
      - {day: 1, period: 8, label: 体比}
      # ……
```

- `days`/`periods` 定义这个年级的网格形状——天数、节数都按年级各自声明，不再假设全局统一的 5 天 × 9 节。
- `periods` 里的 `clock_start`/`clock_end` 是**跨年级比较的唯一锚点**。没有这两个字段，"初一第 3 节"和"初三第 3 节"是不是同一个时间段无法判断，第 5 节讨论的防冲突机制无法正确工作。
- `reserved_slots` 沿用「空课表模板上传」（3.5 节）解析出的教务固定占位格，`label` 是占位课程名，供导出显示，不进求解器。
- 目前 `periods` 按"同一年级每天节次时间一致"的常见情况设计（不逐天单独存一份），如果作息表显示某年级不同天节次时间不同，再扩展成按天存。

日历形状（`days`/`periods` 的 `index`）由「空课表模板」上传解析得到；每节课的真实时钟时间（`clock_start`/`clock_end`）由教务提供的作息时间表补齐——两者是两次不同的输入，都写进同一份 `calendars.yaml`，互不阻塞：模板可以先传、先把网格形状和占位格定下来；作息表随后补上时钟时间，防冲突机制到那时才能生效。

### 3.5 空课表模板上传与占位符识别（修订）

延续本会话更早的讨论，两处修正：

1. **模板必须严格照抄现有 `课程表模板.xlsx` 的结构**（星期/节次表头、每班一行），不再用简化的单行网格。之前设计的方案 A（年级级单一网格）作废。
2. **占位符识别对照课程目录校验，不再是"非空格子=占位"的脆弱判断。** 依赖 3.1/3.2 节的课程登记——格子里的文字必须能在课程目录里找到一个 `external: true` 的课程才算合法占位符；解析结果里对不上号的文字要在回显确认环节明确标出来，让教务核实（是新占位符课程没登记，还是数据本身有误），不能静默吞掉。

### 3.6 跨年级教师占用记录（新增，SQLite）

这是本设计里**唯一建议进数据库、不进 YAML 的部分**。理由见第 4 节。

概念表 `committed_slots`（字段先定方向，不是最终 DDL）：

| 字段 | 说明 |
|---|---|
| `grade` | 产生这条占用记录的年级 |
| `teacher` | 教师姓名（与现有 `TeachingTask.teacher` 同一套身份，纯字符串） |
| `weekday` | 星期索引（0 起），具体对应哪几天以产生这条记录的年级自己 `calendars.yaml.days` 为准——不假设全年级统一 5 天 |
| `clock_start` / `clock_end` | 真实时钟时间，来自该年级 `calendars.yaml` 里对应节次的定义 |
| `course` | 课程名，仅供人工核对用，不参与冲突判断 |

写入时机：某年级的候选方案被教务"确认排定"（见 4.4，这是需要新增的动作，现在系统里没有）时，把该方案里每位教师的全部占用，按该年级 `calendars.yaml` 翻译成真实时钟时间，整批替换掉这个年级此前写入的记录（先删后插，避免重新排定后留下陈旧数据）。

### 3.7 单双周配对课程（修订现有机制，不是新建）

讨论课程设置时发现，现有的"心美"单双周机制（美术单周、心理双周合并成一格）**配对关系和方向是写死的，不是可配置的**，只支持这一对课程，教务没法照着同一套逻辑再配一对新的。这一节明确哪些部分要改、哪些部分维持不动。

#### 3.7.1 "合并成一格再排课"这件事已经实现，不用重新设计

已经查证现有链路：

1. 某课程周课时填 0.5 → `importer.py` 生成 1 条 `TeachingTask`（`periods=1`，带 `parity` 标签）
2. `compiler.py` 的 `_compile_alternate_weeks`（`alternate_weeks` 规则的编译函数）：按班分组，把配对两门课在同一班的任务变量约束相等（`x[A, slot] == x[B, slot]`），逼两条任务落在同一格
3. 因为两条任务 parity 不同，`_add_class_no_clash` 按 parity 分开算冲突，"同一格"不会被判成班级重课——这就是"隔周共用同一格"的物理实现
4. `verifier.py` 的 `_check_alternate` 独立复查：每班这两门课占用的格子集合必须相等

这四步**都是通用的**——`alternate_weeks` 规则只认 `params.pair` 里给的两个课程名，不关心具体是哪两门课，不需要改一行代码。

#### 3.7.2 真正写死的地方：pair 从哪来、方向怎么定

- `ruletext.py` 解析"排课要求"列里表示单双周合并的中文时，`pair` 是硬编码的 Python 字面量 `['美术', '心理']`，不是从配置读的——不管 Excel 里那句话说的是哪门课，生成的规则永远绑定这两个名字。
- `importer.py` 有两处（主导入路径 + 预览核对路径，各自独立实现）在做"周课时 0.5 → 查 `courses.yaml` 的 `alternate` 字段拿单周/双周 → 按班号奇偶各半翻转"这套逻辑。按班号奇偶翻转的前提是"一位老师带的班级恰好在班号奇偶上分布均匀"——这在当前数据上凑巧成立，不是保证，换一批教师任课分布就可能失效，重新掉回"该老师整学期只在单周（或双周）有课"的坑（`CLAUDE.md` 坑 3）。

#### 3.7.3 数据模型改动

- `Course` 去掉 `alternate: Optional[str]`（'单周'/'双周'/None）这个静态方向字段，改成 `alternate_pair: Optional[str]`（配对课程的名字）。
- 双向对称校验：A 说配 B，B 必须指回 A，保存时（`PUT /api/config/courses`）拦下不对称的配对。
- 两边 `family` 必须一致：课时统计按学科系走（坑 1），配对两门课如果学科系不一样，"这一对算一节"在统计口径上就说不通。
- 课程周课时允许填 0.5（`plans.yaml`/Excel 的"周课时"列本来就已经支持 0.5，这次不用改，只是把"0.5 就必须有 alternate"的校验换成"0.5 就必须有 alternate_pair"）。
- **不再需要在课程定义里预先声明谁单周谁上双周**——方向由 3.7.4 的算法在导入时按教师负荷动态决定，不是配置时的静态属性。

#### 3.7.4 教师负荷均衡算法（替换按班号奇偶翻转）

给配对课程涉及的**每一位老师**维护一个"单周节数 − 双周节数"的余量计数器。按班级顺序（如班号）逐个决定这个班的方向：看这个班两门课各自的老师当前的余量，优先把节次分给余量更小（欠得更多）的那一位老师所在的方向，分完更新两边计数器。

保证：不管班号怎么分布、老师带哪些班，每一位相关老师自己的单双周节数差最多相差 1——是算法保证，不是"希望班号分布凑巧均匀"。

#### 3.7.5 需要改的文件（承接实施阶段）

| 文件 | 改动 |
|---|---|
| `scheduler/core/models.py` | `Course.alternate` → `Course.alternate_pair` |
| `scheduler/config/courses.yaml` | 美术/心理改用 `alternate_pair` 互指 |
| `scheduler/core/ruletext.py` | `pair` 从写死的字面量改成"这一行的课程 + 它的 `alternate_pair`" |
| `scheduler/core/importer.py` | 两处 0.5 课时处理逻辑：找配对课程改查 `alternate_pair`；方向判定换成 3.7.4 的贪心余量算法 |
| `scheduler/core/config.py` | `resolve_plan_key` 现在靠 family+`alternate` 排序找两个成员，改成靠 `alternate_pair` 找；找到即可，顺序不影响语义（方向是导入时动态定的） |
| `scheduler/core/compiler.py`、`scheduler/core/verifier.py` | **不用改**——`alternate_weeks` 规则和"共用一格"的约束已经是通用实现 |
| `CLAUDE.md` 坑 3 | 现在的表述"按班号奇偶各半翻转...使每位美术/心理老师单周双周各教一半的班"不再准确，需要重写成 3.7.4 描述的算法保证 |

## 4. 关键机制

### 4.1 为什么跨年级防冲突走"复用 `Teacher.forbidden`"而不是"合并求解模型"

`Teacher.forbidden`（教师级禁排 `[day, period]` 对，来自 Excel"不能排课节次"列）已经是 `precheck.py`/`compiler.py` 认得的硬约束输入。跨年级占用本质上就是**再多一批禁排格子**——排某个年级之前，把这位老师在其他"已确认排定"的年级里占用的真实时间，翻译成当前年级自己的格子编号，并入他的 `forbidden` 列表，编译器/校验器不需要改一行约束逻辑。

这比合并成一个跨年级 CP-SAT 模型（`CLAUDE.md` M7 那条路）轻量得多，也更贴近教务的实际工作方式：一个年级一个年级地定，不是三个年级一起拍板。如果将来真的需要三年级联合优化（而不只是防止冲突），那是另一个量级的需求，到时候再评估要不要走 M7 那条路。

### 4.2 时间匹配用"区间重叠"而不是"字段相等"

学校常见的做法是不同年级错峰上下课（减少走廊拥堵），也就是说初一第 3 节和初三第 3 节即使都叫"第 3 节"，时钟时间也可能是错开的、部分重叠的，不是恰好相等。

翻译"这位老师在别的年级占了哪些真实时间"到"当前年级的第几节要禁排"时，判定标准必须是**时间区间重叠**（`committed.clock_start < period.clock_end and committed.clock_end > period.clock_start`），不能要求 `clock_start`/`clock_end` 完全相等。用相等判断会在错峰排课的学校里漏掉真实冲突。

### 4.3 求解流程里"确认排定"是一个新动作

现在的求解流程是：发起求解 → 拿到多个候选方案 → 教务挑一个 → 导出 Excel。没有任何一步把某个候选"钉死"成这个年级的正式课表——导出只是生成文件，不改变系统状态。

跨年级防冲突要求：教务选定一个候选后，除了导出，还要有一个**确认排定**的动作，触发把这份课表写进 3.6 节的 `committed_slots`。这是全新的 API/UI 表面，现在完全没有，需要单独实现（本文档只定方向，不展开具体交互）。

### 4.4 求解某年级时如何应用跨年级约束

排年级 G 之前：

1. 查 `committed_slots`，过滤 `grade != G`（不能拿 G 自己之前确认排定的记录来约束 G 这次的重新求解，否则 G 永远没法改自己的课表）
2. 按教师姓名分组，得到"这些老师在别的年级已经占用的真实时间段"
3. 对 G 的每一位相关教师，用 4.2 节的区间重叠规则，把这些时间段翻译成 G 自己 `calendars.yaml` 里对应的 `(day, period)`
4. 翻译不出对应节次的（比如别的年级占用的时间段，G 这一天根本没有课），直接跳过——G 这个时间没有课，谈不上冲突，不需要特殊处理，这是安全的默认行为
5. 把翻译出来的格子并入该教师的 `forbidden`，其余照常走现有预检/编译/校验流程

### 4.5 没有强制求解顺序

不要求"必须先排初三再排初一"这类固定顺序。哪个年级先确认排定，就先在 `committed_slots` 里留下记录；后排的年级会看到已确认年级的约束，先排的年级不受后排年级影响（因为后排年级此时还没有 `committed_slots` 记录）。如果两个年级都还没确认过，互相之间自然没有约束可循——这是正常的初始状态，不是异常，不需要报错或提示。

## 5. 存储选型：为什么只有 `committed_slots` 进数据库

课程目录、课程计划、年级日历都是**教务手工维护的静态配置**，改动频率低（一学期改一次量级），继续留 YAML：

- 符合 `CLAUDE.md` 已经定下的哲学——"规则是数据，不是代码"，教务除了走 UI，理论上还能直接打开文本编辑器改，也方便 `git diff` 看懂每次改动
- 这次课程设置的增删改查已经验证"整份读出来 → 校验 → 整份写回去"这套模式在这个数据量级下足够健壮
- 为了这点数据量单独建表，只是把简单问题复杂化，没有实际收益

`committed_slots` 不一样：

- 它不是教务手填的配置，是**求解结果确认后的副产物**，不需要人手改
- 它需要被**频繁、跨年级地查询**——排任意一个年级之前都要按教师姓名把其他年级的记录捞出来做区间匹配。这是结构化查询问题，不是配置读写问题，硬摊在 YAML 里做等于在代码里重新发明一个简易查询引擎
- 项目里已经有 SQLite（`settings_store.py`），不是引入新技术栈，只是多开一张表

## 6. 对已完成工作的影响

课程设置的增删改查（3.1 节）不受影响，继续留在 YAML 这条路上，不需要推翻重做。

3.7 节的单双周改动会碰已实现的代码，不是纯新增：`Course.alternate` 字段改名要动 `courses.yaml` 现有数据、`ruletext.py`/`importer.py` 现有解析逻辑、`config.py` 的 `resolve_plan_key`，以及一批现有测试（凡是断言"按班号奇偶翻转"这个具体行为的测试都要跟着改断言，不只是加测试）。`compiler.py`/`verifier.py` 不受影响。

## 7. 待确认事项

## 8. 实施拆分建议

以下几块彼此独立，可以分开交付、分开测试，不需要一次性全部做完：

1. 课程系下拉选择 + 重命名（3.2 节）——纯前端改动，复用现有 `PUT /api/config/courses`
2. 课程计划增删 UI（3.3 节）——`SettingsPanel.vue` 加 course picker，后端不用改
3. 空课表模板上传解析（3.5 节）——依赖课程目录已经能登记占位符课程（已满足），可以独立开工
4. 年级日历数据模型 + `calendars.yaml`（3.4 节）——网格形状部分可以先做（从模板解析得到），时钟时间部分等作息表
5. 跨年级防冲突（3.6、4.1-4.5 节）——依赖 4 完成时钟时间部分，是这几块里最后一个能落地的
6. 单双周配对课程改造（3.7 节）——不依赖前面几块，可以独立开工，但要碰现有代码和现有测试，工作量比看起来大，建议单独一个 PR
