# 求解会话持久化与历史列表 — 设计文档

## 1. 目标与范围

现状：`scheduler/api/sessions.py` 里 `ImportSession`（导入预览会话）和 `SolveJob`（求解任务）都是纯内存态的 Python 对象，存在进程内的字典里。模块文档字符串明确写着"批次一是本地单用户工具，重启即清空"——这是当时的既定决定。

本项目要推翻这个决定：**重启不清空**，并且支持**查看历史上多次导入 / 求解，逐条查看、逐条删除、按类型整体清空**。

这是"课表拖拽调整与实时冲突检测"（另一份设计文档）的地基——拖拽功能要在已持久化的 `SolveJob.solutions` 上做局部调整，如果求解结果重启就丢，拖拽功能也无从谈起。两个项目按此依赖顺序实施：先落地本项目，再建拖拽功能。

**不做的事**：多用户/多设备协作、并发写入冲突处理（这仍然是本地单用户工具，见待确认事项）、导入预览与求解任务之间的关联追溯（比如"这个求解任务是从哪次导入产生的"——如果后续需要再加）。

## 2. 现状问题

`scheduler/api/sessions.py`：

```python
class SolveJob:
    def __init__(self, job_id: str):
        self.job_id = job_id
        self.status = 'pending'
        self.issues: List[dict] = []
        self.conflict: Optional[str] = None
        self.solutions: List = []
        self.violations: List[List] = []
        self.dataset = None
        self.cfg = None
```

`_jobs: Dict[str, SolveJob]` 和 `_imports: Dict[str, ImportSession]` 都是模块级内存字典，进程重启即空。`ws.py` 的 `_run_job` 还会额外挂一个 `job._queue`（`asyncio.Queue`，给 WebSocket 端点转发事件用）——这个字段是运行时的连接管道，**不属于持久化范围**，重启后重新连接 WebSocket 时应当是空的初始状态，不需要恢复。

## 3. 存储设计

复用项目里已有的持久化模式（`scheduler/core/settings_store.py`：Python 内置 `sqlite3`，存在用户目录 `~/.scheduler/scheduler.db`，不进 git，打包成 PyInstaller 单 exe 后依然可用，零新依赖）。新增 `scheduler/core/session_store.py`，两张表：

```sql
CREATE TABLE IF NOT EXISTS import_sessions (
    token TEXT PRIMARY KEY,
    grade TEXT NOT NULL,
    created_at TEXT NOT NULL,   -- ISO 8601
    data TEXT NOT NULL          -- ImportResult 的 JSON 序列化
);

CREATE TABLE IF NOT EXISTS solve_jobs (
    job_id TEXT PRIMARY KEY,
    status TEXT NOT NULL,
    grade TEXT NOT NULL,
    created_at TEXT NOT NULL,
    data TEXT NOT NULL          -- {dataset, cfg, rules, solutions, violations, issues, conflict} 的 JSON
);
```

`data` 列里除了 `dataset`/`cfg`/`rules`/`solutions`（`List[Solution]`）/`violations`（`List[List[Violation]]`）之外，`issues`（`List[dict]`）、`conflict`（字符串或 `None`）也一并放进这个 JSON blob，不单独开列——这些字段小、不需要单独查询，跟着一起序列化最简单。

序列化方式：`dataset`/`cfg`/`rules` 里的每一项、`solutions`/`violations` 里的每一项都已经是 pydantic `BaseModel`，用 `model_dump()` 转成可 JSON 化的 dict，整体套一层 `json.dumps`；读回来时反向 `json.loads` 后用各自的模型类重建（`Dataset(**...)`、`SchedulerConfig(**...)`、`[Rule(**r) for r in ...]`、`[Solution(**s) for s in ...]`、`[[Violation(**v) for v in vs] for vs in ...]`）。

不维护额外的进程内内存缓存层——数据量小（单用户、几个并发任务量级），每次读写都直接走 SQLite，避免"内存缓存与磁盘不同步"这类风险，简单优先。

## 4. `sessions.py` 改造

保留现有函数签名（`save_import`/`get_import`/`create_job`/`get_job`），内部实现从操作内存字典改成读写 `session_store.py`：

```python
def save_import(result, grade: str) -> str:
    token = uuid.uuid4().hex
    session_store.save_import(token, grade, result)
    return token

def get_import(token: str) -> Optional[ImportSession]:
    return session_store.load_import(token)   # 找不到返回 None

def create_job() -> SolveJob:
    job = SolveJob(uuid.uuid4().hex)
    session_store.save_job(job)
    return job

def get_job(job_id: str) -> Optional[SolveJob]:
    return session_store.load_job(job_id)
```

`ws.py` 里 `_run_job` 每次调用 `on_candidate`、以及到达终结状态（`done`/`error`/`infeasible`/`timeout`/`precheck_failed`）时，除了原有的 `emit(event)`，还要调 `session_store.save_job(job)` 把最新状态落盘。`job._queue` 这个运行时字段序列化时直接跳过（不是 pydantic 模型，也不该持久化）。

新增（供历史列表用）：

```python
def list_imports() -> List[dict]:      # [{token, grade, created_at}, ...]，不带完整 data，摘要即可
def list_jobs() -> List[dict]:         # [{job_id, status, grade, created_at, candidate_count}, ...]
def delete_import(token: str) -> None:
def delete_job(job_id: str) -> None:
def clear_imports() -> None:           # 删 import_sessions 全表
def clear_jobs() -> None:              # 删 solve_jobs 全表
```

`list_jobs` 的 `candidate_count` 从 `data` JSON 里数 `solutions` 的长度取，不需要单独列。

## 5. API 端点

```
GET    /api/imports              历史导入列表（摘要）
GET    /api/imports/{token}      单条详情（现有 /api/import/confirm 已经用 token 读取，这里补一个只读查看的端点）
DELETE /api/imports/{token}      删单条
DELETE /api/imports              清空全部导入历史

GET    /api/solve/jobs           历史求解任务列表（摘要）
GET    /api/solve/{job_id}       已有端点，语义不变——现在能查到任意历史任务，不只是刚创建的
DELETE /api/solve/{job_id}       删单条
DELETE /api/solve/jobs           清空全部求解历史
```

列表按 `created_at` 倒序返回（最新的在最上面）。

## 6. 前端

不新增顶级页签。现有 `App.vue` 是"导入"/"课程"/"排课"这类单页签切换的结构，历史记录按类型分别挂在对应页签里：

- "导入"页签顶部加一个"历史记录"入口，点开是导入历史列表，选一条能重新加载回预览界面（复用现有确认导入的流程），也能单条删除、整体清空。
- "排课"页签顶部同理加一个"历史记录"入口，列表项显示年级/状态/候选方案数/创建时间，选一条加载回候选方案课表视图（`CandidateTabs.vue`），能继续切换候选、导出、以及后续拖拽功能要用的入口点。

具体组件先不细分（比如是不是要一个独立的 `HistoryList.vue` 给两处复用），留给 writing-plans 阶段按实际接口形状决定。

## 7. 边界情况

- **并发写入**：不处理。仍然是本地单用户工具，同一时刻只有一个人在操作。
- **WebSocket 重连**：`job._queue` 是连接期间的临时管道，不持久化。如果求解正在进行中时应用重启，这个任务的 `status` 落盘的最后一次快照是重启前的中间状态（比如 `'solving'`），重启后没有机制"续算"——用户只能重新发起一次求解。这个不是本次要解决的问题（CP-SAT 本身没有断点续算的能力），只需要保证：重新打开应用时，看到的是"这个任务卡在 solving，但已经没有活跃的 WebSocket 在推事件了"，不会误导用户以为还在算。前端对着一个 `status == 'solving'` 但连不上 WebSocket 的历史任务，展示成"已中断"，不用做更复杂的处理。
- **数据库文件损坏/首次运行**：`session_store.py` 跟 `settings_store.py` 一样，`CREATE TABLE IF NOT EXISTS`，首次运行自动建表，不需要迁移脚本。

## 8. 测试策略

后端：`session_store.py` 的存取/列表/删除/清空各自单元测试（用临时 SQLite 文件，不碰用户真实的 `~/.scheduler/scheduler.db`）；`sessions.py` 改造后原有依赖它的测试（`test_api_import.py`/`test_api_solve.py`）应该在不改断言的前提下继续通过（存储介质变了，行为不变）；新增的历史列表/删除/清空 API 端点各自测试覆盖。

前端：历史列表组件的渲染、选中加载、删除、清空按钮的行为测试，参考 `CourseSettings.spec.ts` 的写法。
