# 课表拖拽调整与实时冲突检测 — 设计文档

## 1. 目标与范围

`docs/superpowers/specs/2026-08-21-中小学排课系统-design.md` 第 10 节把 M5 定义为 6 个视图（班级课表/教师课表/场地占用/求解监控/诊断面板/规则配置编辑）。本项目**只做其中最核心的一块**：班级课表主视图的拖拽调整，带实时冲突检测。其余 5 个视图不在本项目范围内，留给后续单独立项。

依赖：`docs/superpowers/specs/2026-08-24-求解会话持久化与历史列表-design.md`——拖拽调整操作的是已持久化的 `SolveJob.solutions[index]`，两个项目按此依赖顺序实施，本项目建立在前一个项目已完成的存储层之上。

**目标场景**：教务在候选方案课表（`CandidateTabs.vue` + `ScheduleGrid.vue`）里，把某个班级的某节课拖到同一个班级的另一个时间格，可以连续拖动多处，调整完点"确认"，系统一次性检查这批调整有没有冲突，没问题的生效、有冲突的自动退回原位并说明原因。

**不做的事**：跨班级拖拽（把甲班的课和乙班的课互换）；单双周配对课程（心美）的拖拽；软约束的实时提示（只挡硬约束，跟 `verify()` 本身的语义一致）；教师课表视图、场地占用视图等其余 M5 视图。

## 2. 交互模型

拖拽用 SortableJS（项目技术栈已定），限定在同一个班级的列内（列与列之间禁止拖拽）。拖动过程完全在前端本地完成，**不请求后端**——纯粹是"挪动卡片"：如果目标格子已经有课，就跟当前拖的这节课互换位置；如果是空格子，就直接搬过去。可以连续拖动多处，本地状态持续累积这批"待确认"的调整。

每个正在编辑的班级顶部有"确认"和"取消"两个按钮：

- **取消**：清空这批未提交的调整，本地状态回到上次确认后的样子，不打后端。
- **确认**：把这批调整（`task_id → to_slot` 的列表）一次性提交给后端做实时校验。

后端返回后：被退回的卡片弹回原位，配一个提示气泡说明冲突原因（比如"教师分身：李老师同一时间在 3 班"）；其余调整按后端返回的 `placements` 整体重绘这个班级的列——前端不自己拼状态，服务端返回的就是唯一真相，避免前后端状态对不上。

## 3. 后端算法：只退肇事者

`Violation`（`scheduler/core/verifier.py`）目前不带结构化的 `task_id`/`slot` 引用（`_check_class_clash`/`_check_teacher_clash` 只有 `kind`/`detail` 文字说明），没法从违规结果直接反查"是哪几处改动导致的"。为了不新增一套独立的冲突判断逻辑（避免破坏项目一直坚持的"不重复实现约束逻辑"原则），改动后不去解析违规文字，而是把 `verify()` 当黑盒裁判反复调用：

```
def _apply_and_prune(placements, moves, dataset, cfg, rules):
    """套用 moves，若有冲突则贪心退回肇事者，返回 (最终 placements, applied, reverted)。

    moves: [(task_id, to_slot), ...]，均属于同一 class_id。
    """
    pending = dict(moves)  # task_id -> to_slot，剩余"还没退回"的改动
    original = {p.task_id: p.slot for p in placements if p.task_id in pending}

    while pending:
        candidate = _with_moves_applied(placements, pending)
        violations = verify(Solution(placements=candidate, ...), dataset, cfg, rules)
        if not violations:
            return candidate, list(pending.keys()), reverted
        # 贪心：依次尝试退回 pending 中的每一处改动，选退了之后违规数降得最多的那个
        best_task_id, best_violation_count = None, len(violations)
        for task_id in pending:
            trial = dict(pending)
            del trial[task_id]
            trial_candidate = _with_moves_applied(placements, trial)
            trial_violations = verify(Solution(placements=trial_candidate, ...), dataset, cfg, rules)
            if len(trial_violations) < best_violation_count:
                best_task_id, best_violation_count = task_id, len(trial_violations)
        if best_task_id is None:
            # 没有单独退回任何一处能改善，说明这批改动互相牵连，退化成整体回退
            reverted += [(tid, '与其他改动互相牵连，已整体撤销') for tid in pending]
            return placements, [], reverted
        reverted.append((best_task_id, ...))  # 原因从 best_task_id 退回前后的 violations 差集里取
        del pending[best_task_id]

    return placements, [], []  # moves 为空
```

因为一批改动通常就几处，`verify()` 对单个候选方案的完整课表是毫秒级（性能基线：初三 32 班全量求解都才 0.6 秒，`verify()` 比求解快得多），整个贪心过程（最坏情况 O(n²) 次 `verify()` 调用，n 是改动数）依然是无感知延迟的量级。

**退化情况**：如果贪心找不到"退一个能改善"的选择（说明这批改动互相牵连、没法只退一部分），就整体回退所有改动，给出统一的原因说明。这是诚实的兜底，不强行保证"总能精确只退肇事者"。

**关于"原因"文案**：单独退回某一处后，`violations` 数量下降——下降前后的 `Violation.detail` 差集就是这一处改动"解决"的问题，用它作为退回原因反馈给前端。

## 4. 后端接口

新增同步 REST 接口（不用现有 WebSocket 那套流式机制——这是毫秒级单次请求/响应，不是分钟级的求解任务）：

```
POST /api/solve/{job_id}/candidates/{index}/adjust
Body: { class_id: int, moves: [{task_id: int, to_slot: int}, ...] }
Response: { applied: [task_id...], reverted: [{task_id, reason}], placements: [...这个班级最终的课表...] }
```

实现：`sessions.get_job(job_id)` 取出（依赖项目一的持久化存储），校验 `moves` 里所有 `task_id` 对应的任务确实属于 `class_id`（防御性检查，前端不应该发出跨班级的 moves，但后端不能假设前端诚实），跑第 3 节的算法，把最终 `placements` 写回 `job.solutions[index]`，调 `session_store.save_job(job)` 落盘（复用项目一暴露的存储函数），返回结果。

`rules` 现在已经是持久化 `SolveJob` 数据的一部分（见项目一设计第 3 节），这里直接从 `job.rules` 取，不需要额外改动。

## 5. 边界情况

- **单双周配对课程**（心美：美术+心理占同一格）：这次先不支持拖拽这类格子，前端直接锁定（不响应这些卡片的拖拽事件）——配对课程的拖拽语义（拖一门是不是两门都要跟着动）比较绕，留到以后需要时再单独设计。
- **教务固定占位的格子**（班会、体育课那类 `reserved_slots`）：前端标成不可放置目标，不用问后端——这些格子哪些是教务固定占位是数据本身的事实（`dataset.calendar.reserved_slots`），不是规则判断，不违反"前端不做合法性判断"的原则。
- **并发编辑**：不用处理，本地单用户工具。
- **只挡硬约束**：`verify()` 本来跑的就是硬规则，软约束不影响这次的合法性判定，跟现有校验器的语义保持一致。
- **`moves` 为空**：直接返回 `{applied: [], reverted: [], placements: 现状}`，不调用 `verify()`。

## 6. 前端组件

`ScheduleGrid.vue` 需要扩展出"可编辑模式"（当前是纯只读展示）：接入 SortableJS、维护本地待确认状态、"确认"/"取消"按钮、`reverted` 卡片的弹回动画与提示气泡。具体拆不拆子组件（比如把"确认/取消"控制条独立出来），留给 writing-plans 阶段按实际实现体量决定。

**顺带修复**：`ScheduleGrid.vue` 现在硬编码 `PERIODS_PER_DAY = 9`/`N_SLOTS = 45`（`scheduler/web/src/components/ScheduleGrid.vue:14-15`），是"年级日历参数化"那次分支审查发现的已知遗留缺口（前端从未跟进那次改造）。这次要重写这个组件支持拖拽，顺手从后端返回的候选方案数据里取实际的日历形状（而不是硬编码常量），一并解决——不是本项目的主要目标，但既然要动这个文件，不修就是明知故犯地留着一个已知问题。

## 7. 测试策略

后端：`_apply_and_prune`（第 3 节算法）单独写单元测试，构造几个候选方案 fixture，覆盖"单处冲突全退""多处冲突只退肇事者""改动互相牵连、退化成整体回退""moves 为空"这几种场景；`/adjust` 接口测试覆盖"全部合法直接生效""部分被退回""跨班级 task_id 被拒绝"。

前端：拖拽产生的本地待确认状态、确认后按服务端返回的 `placements` 重绘、`reverted` 卡片弹回并显示原因、取消按钮清空待确认状态这几个行为点，参考 `CourseSettings.spec.ts` 的写法。
